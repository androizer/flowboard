# Web client: performance as data grows

Status: future work based on a code scan of `apps/web/src` on 21 October 2026. No large-data slowdown has been measured, and the optimizations below are not implemented. Start with a production-like dataset and browser profiling before changing behavior.

The current client is intentionally simple for the MVP. It loads an authorized tree, all workspace members, and every page of a selected list's board. The API already paginates board tasks and users, but the client assembles complete arrays before rendering. The workspace overview returns bounded upcoming tasks, while its list rows cover every accessible list. See [web client](modules/web-client.md) and [API/contracts](modules/api-contracts.md) for the current behavior and ownership rules.

## Request lifecycle and correctness at scale

- The selected-list effect in [`Dashboard`](../apps/web/src/dashboard/dashboard.tsx) uses an `active` flag so an old result is not committed, but it does not cancel the HTTP work. A switch away from a large list can leave its page loop consuming bandwidth. Add request cancellation when introducing incremental loading; keep identity changes from replaying old-user requests.
- Offset page loops can observe changing data across requests. `getAllBoardPages` compares status/field JSON between pages but does not establish a task snapshot. For a paged or infinite view, define stable sort and page consistency with the API, handle inserts/moves without duplicates or omissions, and use a configuration revision or equivalent if needed.
- Full refetches after confirmed mutations are currently simple and safe. Any narrower invalidation must still reflect the server's accepted placement, visibility, version, and configuration. Keep error paths that preserve drafts and show the confirmed server state.
- Defer bundle splitting, image work, and animation tuning until network and browser traces show they matter. This scan found data volume and rendered-node count as the more direct risks.

## When to use this guide

1. Reproduce the complaint with realistic accessible-list, task-per-list, member, status, and custom-field counts. Record device/browser, request count and transfer size, time to usable Home/list, React commit time, DOM node count, and memory after navigation.
2. Identify whether delay is API/transfer, JavaScript computation, or DOM rendering. Compare Home, tree expansion, Board, Table sorting/scrolling, task opening, and admin pickers separately.
3. Change one bottleneck at a time. For task growth, start with bounded loading; virtualization alone still downloads and holds all tasks. For container growth, start with tree indexing/collapsed branches, then change the API only if the snapshot remains too large.
4. Verify exact task counts, list-wide sort order, drag placement and anchors, task links, stale-version feedback, permission-filtered navigation, and identity changes. Update the [web client](modules/web-client.md), [API/contracts](modules/api-contracts.md), and relevant module test TODOs when behavior or contracts change.
